# PrintLab: найденные баги и как повторить

**Повторная проверка исправлений:** [версия 1.3.2](bug-fixes-1.3.2.md). Ниже сохранён исходный отчёт.

Проверка 28–30.10.2026, версия 1.3.1. Найдено 8 воспроизводимых проблем. Исправления в приложение не вносились.

## 1. Ответ может уйти другому клиенту — высокий приоритет

Условия: в админском чате есть заказы А и Б от разных клиентов.
1. У заказа Б нажать «Ответить клиенту».
2. Не отправляя сообщение, сделать обычный Telegram reply на карточку заказа А.
3. Отправить текст «Ответ для А».

**Получилось:** текст получает клиент Б. Привязка reply к А игнорируется.
**Нужно:** отправить клиенту А либо предупредить о несовпадении.
Проверено: штатные обработчики, два клиента в изолированной БД. Чужим реальным клиентам сообщения не отправлялись.

## 2. Можно случайно заказать 30 деталей вместо заполнения 30%

Условия: STL загружен, цвет выбран.
1. На выборе количества нажать «Другое количество».
2. В истории нажать «Повышенная · 0,12 мм».
3. На появившемся экране заполнения отправить `30` текстом.

**Получилось:** количество 30, заполнение остаётся 15%. Старый ввод количества не сбросился.
**Нужно:** число относится к видимому шагу либо бот просит выбрать кнопку заполнения.
Проверено: Telegram + обработчики, заказ №17; H2/PostgreSQL.

## 3. Старая кнопка создаёт второй заказ без предупреждения

Условия: уже есть незавершённый STL-заказ с моделью.
1. Найти старое сообщение согласия перед заказом по фото.
2. Нажать «Продолжить».

**Получилось:** создаётся новая заявка по фото; прежний STL-черновик остаётся, предупреждения нет.
**Нужно:** подтверждение начала нового заказа.
Проверено: обработчики production, №18 → №19; H2/PostgreSQL. Именно клик в Telegram автоматизировать не удалось.

## 4. Неверный промокод создаёт пустой заказ

Условия: нет незавершённого черновика; может быть заказ в ожидании оплаты.
1. Отправить `/promo UNKNOWN` или недоступный `/promo FIRST30`.
2. Открыть «Мои заказы».

**Получилось:** промокод отклонён, но появился пустой черновик. Аналогичный путь есть у `/quantity -1`.
**Нужно:** при ошибке новый заказ не создавать.
Проверено: Telegram/БД, №17; H2/PostgreSQL для UNKNOWN.

## 5. Ответ клиента прикрепляется к другому его заказу

Условия: у одного клиента заказы А и Б.
1. В заказе Б нажать «Написать сообщение».
2. Сделать обычный reply на сообщение бота по заказу А.
3. Отправить текст.

**Получилось:** сообщение зарегистрировано по Б, хотя reply сделан по А.
**Нужно:** учитывать явно выбранное сообщение либо запросить уточнение заказа.
Проверено: изолированные H2/PostgreSQL.

## 6. После «Изменить способ доставки» старый ввод остаётся активным

Условия: стоимость рассчитана, клиент выбирает получение.
1. Выбрать СДЭК курьером, дойти до запроса ФИО.
2. Нажать «Изменить способ доставки».
3. Написать `Как выбрать самовывоз?`.

**Получилось:** фраза сохранена как ФИО, бот запрашивает телефон вместо реакции на экран выбора.
**Нужно:** отменять старый ввод при возврате к выбору способа.
Проверено: изолированные H2/PostgreSQL.

## 7. Самовывоз можно «отправить СДЭК»

Условия: тестовый заказ с самовывозом оплачен и готов.
1. Админ: «Изменить статус».
2. Нажать «Отправлен».

**Получилось:** клиенту «Заказ отправлен СДЭК», хотя выбран самовывоз.
**Нужно:** для самовывоза показывать выдачу/выполнение без уведомления СДЭК.
Проверено: полный платёжный цикл в изолированных H2/PostgreSQL.

## 8. Команда меняет удалённый оплаченный заказ

Условия: оплаченный тестовый заказ удалён через админку, его номер N сохранён.
1. Отправить в админский чат `/status N PRINTING`.

**Получилось:** скрытый заказ переходит в работу без восстановления. Кнопки админки это запрещают, команда обходит проверку.
**Нужно:** сначала требовать восстановление.
Проверено: изолированные H2/PostgreSQL. Доступ только у администратора.

## Оплата и реквизиты: что проверено

В Telegram: расчёт №18 → самовывоз → публикация оператором → подтверждение клиентом → тестовые реквизиты из группы → ответ клиента. Реквизиты и ответ доставлены.

В группе отклонены: сумма на 1 копейку меньше, идентификатор `AB`, переход до оплаты сразу в работу или выполнение.

В изолированных БД: «Оплачен» → «Деньги поступили» → ввод идентификатора → в работе → готов → отправлен → выполнен → полный возврат. Повторные кнопки, повтор платежа, неверные идентификаторы и выход назад проверены. Второго платежа нет.

FIRST50/FIRST30: повторные применения не складывают скидки; до оплаты квота не тратится. Проверены 2 оплаты FIRST50, затем 8 FIRST30, отказы следующему клиенту, повтору того же клиента и гонка за последним местом. Это тестовые БД.

**Риск процесса:** последний слот промокода не резервируется до оплаты. Два клиента могут получить цену со скидкой, но учесть оплату с ней сможет только один. Если второй уже перевёл деньги, потребуется вручную согласовать цену/возврат.
